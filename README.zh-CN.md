# Ichiwatashi（一渡始）

像素画的**确定性测量**与**参数化构建**。

## 这是什么，以及为什么测量在前

generate-judge-refine 这个循环里，**judge 必须早于 generator**。这里是那个 judge，以及一个循环
实际会用到的构建、调色板、帧三块。

**顺序不是偏好。** 把这版判据第一次指向一张**已知优秀**的精灵时，它立刻证伪了自己两条假设：

| 假设 | 实测说了什么 |
|---|---|
| 「孤立像素越少越好」 | 真实 72×113 格斗帧有 **10.1%** 孤立像素（312 个），而手绘只有 **1.35%**。**好画看起来更差，因为那是绝对数而两张图尺寸不同。** 按比率算好画仍更"脏"，而**那是对的**：21 色、546 个色块，那些像素**就是细节**——单像素高光、眼睛、布料纹理。所以这个指标要**比率 + 色块形态**才能分噪声与细节，而只看比率会在好画上**误报**。 |
| 「描边是单一色 = 有纪律」 | 好画 **0.662**，手绘 **0.991**——**而好画是对的。** 商业像素画的描边会随局部颜色变化：头发偏冷、布料偏暖。**单一平色描边是业余做法。** 这条指标是反的。 |

**这两条若被训进模型，就会变成"标准答案"**，而**不拿一张已知优秀的样本去对照，两条都看不见**。
这就是本仓库先做测量工具的全部理由。

## 安装与使用

```bash
pip install -e .
ichiwatashi judge sprite.png                  # 测量
ichiwatashi palette sheet.png --count 16 --merge 24 --saturate 2.0
ichiwatashi build sprite.json --out sprite.png --preview sprite_x8.png
ichiwatashi frames ./frames --out loop.apng --duration 40
```

Pillow 是硬依赖：一个读写图像却打不开 PNG 的工具不是"降级"，是坏的。

### 三条要点

**`--merge` 是重点。** 一件 40 帧 JPEG 报出 **25,398 个不同 RGB 值**，而清单开头是 `#005D77`
跟着 `#005E77` / `#015C77` / `#005D76`——一个色加它的压缩光晕。按每通道 24 归并，才回到作者
真正用的那 10 来个色。`--merge 0` 可以关，而那是**在量编码器**。

**两块板是不同的东西。** 材料板（从参考图采样，画的时候用什么色）与辨识板（按用途选，
靠哪几个色认出是谁）。按频次采样得到的是**色彩分布**，而分布里大部分是两个角色**共用**的区域。
两张设定图采样：共用色 0、中位距离 0.303，而**最小距离 0.026**——那一对是白髪与近黑描边，
**两个角色都有**。而小尺寸下被认错的就是最小那一对。

**形状优于逐格摆放，是对"还控不住逐格"的作者而言。** 手写 32×32 两次都出来认不出的方块；
同一个精灵写成锥 + 圆 + 梯形，第二次就可读了——**因为比例错了变成改三个数字，而不是重摆几百个
像素**，而迭代才是收敛的原因。这不构成"形状优于手"的主张：能刻意摆像素的人会赢过它。

**描边那一步不是装饰。** 没有它，小尺寸下剪影会化进背景。它在这里是自动的，理由与它存在的
理由相同：**它是规则，不是决定。**

### 帧与枢轴

`frames` 会报 **drift**（内容相对锚点漂了多少）——那个数就是"动画会不会抖"。

两种正当做法，实测自两件真动画：**固定画布**（锚点隐含在画布，代价是纹理，背景占 75.7%）与
**逐帧紧裁 + 存枢轴**（代价是枢轴必须对，错了就漂）。小循环用前者，大位移一次性动作用后者。

**而枢轴怎么验**：不看那个数字。把同样几帧在同一画布上排两次——一次按存的枢轴、一次按帧中心——
比较。枢轴对齐让脚落在一条水平线上，中心对齐让它们漂浮。**声称了枢轴却从不与替代方案对照，
那只是一个带故事的数。**

## 刻意不包含什么

**没有模型，也没有训练。** 让像素画读起来像像素画的东西，大部分可以从像素本身数出来，而可数的
答案更快、可解释、不会漂移。只有"这张脸可爱吗"这类判断需要学到的模型，而那是整体的一小部分。
可测的部分都在这里；不可测的部分没有被假装出来。
